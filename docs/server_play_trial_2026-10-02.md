## 问题清单（只记现象和证据，不含设计）

**响应速度**
1. 每一步都要等模型来回一次。按 claude 会话记录拆分，模型每走一步约 1.5–2 秒（Opus／Sonnet 都是 low），工具本身执行只要约 10 毫秒。拿原木一次要 7–8 步，挖放一次要 6–7 步。
2. 托管程序收到聊天后，会先攒 1.5 秒（`BATCH_DELAY_MS`）再交给模型；从玩家发消息到模型开始处理约 2 秒。
3. 每个会话第一次用某个工具前，都要先调一次 ToolSearch 查找工具，每次多花约 1–3 秒。叫停会结束旧会话，所以叫停后的第一个任务又要重新查找。
4. 叫停后会结束旧会话、开新会话，新任务要等 claude 冷启动（约 3 秒）并重新读一遍状态。
5. 上下文涨得快：查到的状态和动作完成通知都带着完整物品数据。这次从 48k 涨到 91k；上一轮 C 实测一个会话从 48k 涨到 108k。
6. 模型已经确认过的动作完成通知，会再触发一轮（约 3–4 秒），费用也跟着多。

**流程**
1. 没有找附近方块或箱子的能力，只能一格一格查。用户口头说"旁边的箱子"时，这次就失败了。
2. 做事前不先回一句话：拿原木那次、挖放那次，用户都是干等十几到二十秒才听到第一句。只有打招呼那步是先回话再动。
3. 开箱、取物、关箱、选槽、看向、丢出这类常见流程，要拆成很多次单独的工具调用，每次都要完整抄写物品数据。
4. 旧的模型进程收到叫停后，5 秒都不自己退出，要被强制结束。这次身体在同一秒就停了，不影响结果，但新任务要等这段收尾结束才开始。

**准确性**
1. Opus 和 Sonnet 都说过"箱子里另有 3 颗钻石"，其实钻石在小克自己背包里（只出现在命令行小结里，没对玩家说）。读容器视图时，会把自己背包那几格当成箱子里的东西。
2. Sonnet 有一次生成的工具参数格式坏了（`__unparsedToolInput`），重试后成功，多花约 6 秒。

**模型对比**（样本少，只能参考）
- 同类的拿原木任务：Opus 那次因为找不到箱子没完成，Sonnet 给了坐标后用 22 秒完成，没看出 Sonnet 明显更快。
- 两者每一步的耗时接近，慢主要是因为步数太多，换模型解决不了。
- 默认模型要不要改成 Sonnet 5.5 low，等用户决定；这次没改任何默认配置。
