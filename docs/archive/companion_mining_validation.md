# 持续陪挖：程序矩阵验收（2026-10-06）

对应 [交付计划](../delivery_plan.md) 第 2 步「查清陪挖 `COMPANION_OUT_OF_RANGE`」。10-05 的首轮记录见 [10-05 交付计划快照](delivery_plan_2026-10-05.md) 第 7 行。

## 结论

`COMPANION_OUT_OF_RANGE` 的根因是**掉落物的范围检查太严**，不是暂停/恢复本身的问题。修正后，隔离服上的完整程序矩阵（10 个场景、24 项检查）连续两轮全部通过。真实模型（Codex/Claude）陪挖没有跑，留到第 3 步请用户验收时做。

## 根因

陪挖的范围规则是：以绑定玩家为圆心、半径 `radius`（3 或 4 格）内，Bot 自己的位置、路线和要挖的矿都必须在圈内。拾取掉落物时，服务端又额外要求**掉落物本身**也在这个圈里：`CompanionMiningGuard.validatePickup` 一处，随同下发的 `CompanionPickupGuard` 又一处。

矿石被挖掉后，掉落物会弹出、在地上滑一段。矿在圈的边上时，掉落物很容易滑出圈外。复现时（`--case=pause-resume-preserves-budget`）：

| | 位置 | 离玩家 |
| --- | --- | --- |
| 玩家 | 6412.5, 201, 6412.5 | — |
| 第二块矿（中心） | 6414.5, 201.5, 6415.5 | 3.64 |
| 掉落的煤 | 6414.94, 201, 6415.98 | **4.25** |
| Bot | 6414.02, 201, 6413.25 | 1.66 |

煤离矿中心不到 0.7 格，Bot 站在圈内（比如 6414.5, 6415.5 这一格）就能捡到，但服务端在下发拾取的第一刻就以 `Body or bound mining target left the live companion radius` 拒绝了。10-05 那次失败是同一个原因（当时是第一块矿，所以看起来像「挖 1 块、拾取 0」）。运行端这边原本允许掉落物比半径多 0.75 格（按网格中心水平量），两端规则也不一致。

## 修正

- 服务端：陪挖产生的掉落物，允许比半径多 `CompanionMiningGuard.DROP_REACH_MARGIN = 1.5` 格（到玩家的三维距离）。掉落物仍必须在源矿 3 格内（证明是这块矿掉的）。Bot 的位置、路线和站位**仍然只能在半径内**，没有放宽。站不进圈内又够不着的掉落物，照样拒绝，不会追出去。
- 陪挖拾取时随同下发的 `CompanionPickupGuard` 用同一个余量；普通跟随拾取（`companion-pickup`）不变，掉落物仍须在半径内。
- 运行端：陪挖子任务认掉落物的范围改成「到扫描时玩家位置 ≤ 半径 + 1.5」，和服务端一致。
- 实服脚本：失败或 unknown 的回执现在会留下摘要、结果（含导航诊断）和最近一次观察（Bot、玩家、地面物品的位置），以后排查不用再猜。最后一个场景原来用半径 4 搜新矿，但硬停后 Bot 停在约 6410.7，新矿在 4.7 格外，搜不到；改成半径 6。这个场景以前没跑到过（矩阵总是停在第 2 个场景）。

## 没有测的

- 自然矿洞、长时间陪挖：矩阵是受控的平地夹具。
