### 真人体验后的交互设计（2026-10-02，分批交付）

用户明确：旧架构中同类模型能快速响应；模型生成速度足够快，本轮处理的是新架构的交互设计问题，不通过换模型或降低思考档位解释、回避。以下描述完整目标；第一批已经实现的范围以勾选项和本节交付记录为准，不能将后续设计当作已完成。

**第一批（本轮约30分钟）交付。** `discover-containers` 返回附近候选和短期引用；`container-list`／`container-withdraw`／`give-item`／`fetch-and-give` 在运行端完成连续核验。真实隔离服测试以2次 MCP 调用完成“发现＋取3原木丢给玩家”，测试客户端和RCON各自确认实收3、箱剩5，自身钻石未被算入箱内。近距单样本工具链166.54ms到权威丢出、2666ms到测试玩家背包确认；这些数值不含模型推理、工具发现或游戏聊天调度，**不是模型回复延迟或性能对照结论**。详见[本轮证据与限制](server_interaction_validation.md)。

第一批当时范围：箱子可触及、接收者2格内，不自动走近、不能识别同状态换箱。第二批已补走近和实例核验，见后文；仍只从单个足量源栈转入空快捷栏，不跨栈或按variant编号选择变体。任务只确认丢出，指定玩家拾取仍标未确认；独立测试实收不等于产品已有通用拾取归因。

**源码对照。** 旧 `mcp-server/src/tools/action-tools.ts` 的 `give-item` 内部完成走近、看向和丢物，`container-withdraw` 内部完成走近、开箱、取物、关箱，`container-list` 只汇总 `containerItems()`；`observe.ts` 和 `find-blocks` 已提供附近目标／相对位置。新 `client-runtime/src/mcp.ts` 把选槽、点击、窗口版本和完整组件直接交给模型；`SurvivalActions.container()` 又把箱子槽位与 Bot 背包平铺。新身体的控制验证通过了，但原有面向任务的 Interface 没有一并迁移。复用这些语义和流程，不直接复制旧实现中依赖 Mineflayer 或仅按物品 ID 聚合的假设。

**职责。** Agent 负责理解请求、选定目标、处理歧义和交流；Agent 主机上的共享任务 Module 负责确定性多步执行、现场核验、互斥、取消和结果归集；Body／游戏 Adapter 负责真实观察、原版交互与权限保护。Claude、Codex 和后续原生 API 复用任务 Interface。MC 服务器不运行模型、不持有模型凭据，本机无需新增 MC 客户端。

以“把旁边箱子里的 3 个原木给我”为第一条完整流程：

| 阶段 | 玩家体验 | 程序与模型分工 |
| --- | --- | --- |
| 收到请求 | 能知道请求已进入处理，不静默等待整项任务结束 | 空闲时及时派发明确聊天；如显示宿主回执，使用独立的 MCBOT 系统状态，不冒充小克已理解或答应任务 |
| 理解与回应 | 小克先自然回应“我看看旁边的箱子”，或提出一个必要的问题 | 模型决定意图；可在一次任务提交中携带自己的简短回应，运行端按顺序发言、开始操作，减少为“先回应”额外增加的往返 |
| 定位目标 | 唯一合理目标直接使用；有两个候选时问“左边还是靠墙那个” | 一次有界附近发现返回带来源的候选、相对位置与短期引用；明确以发言玩家还是 Bot 为中心，不能默认二者位置相同；不让模型逐格猜坐标 |
| 完成任务 | 能连续走近、开箱、取物、关箱、走近玩家并交出物品 | 模型提交来源、物品、数量、接收者；任务 Module 执行已授权范围内的确定性步骤，过程中不要求模型逐槽操作或复制 NBT；每个步骤仍经原版规则和完整核验 |
| 遇到变化 | 简短说明缺什么、哪一步受阻、已做了多少 | 重读实际状态；只有仍在原授权范围且结果明确时才继续。目标歧义、特殊物品变体、权限拒绝、范围外路线或 unknown 需要停止并回报，不盲重试 |
| 完成与叫停 | 得到一次明确结果；随时说“停”都有效，之后的新话不会丢失 | 终态按任务／会话标识去重；叫停先撤销控制、阻止后续步骤，再处理 Agent 取消。已经发生的世界改动不自动回滚，收尾期间的新明确消息入队并仅投递一次 |

**观察与目标引用。** 默认观察只给相关玩家、附近目标、当前任务和物品摘要；详细数据按需。附近发现先做小范围、候选数和工作量都有上限的实现，只看已加载区域，标注可见／遮挡／未知，不隐式生成区块、不读未打开箱子的内容。无法确定目标就澄清，不把“当前没找到”表述为世界中不存在。箱子、Bot 背包和 carried 必须在字段及摘要中明确分组；槽位归属以真实库存身份和已验证菜单契约判断，不硬编码末尾 36 格，不按 Mod 名称猜语义。

完整 typed-NBT、菜单版本和栈快照留在运行端／游戏端。给模型的短期引用只是查找实际快照的随机标识，不是校验凭据、更不是哈希或指纹；仍需绑定身体、实例、世界／维度、会话、控制代次、实体／方块／菜单来源，每次写操作前比较实际字段。过期引用不得悄悄指向另一个箱子或物品。普通无关数量变化可以在任务原授权内重新核验；组件变体改变、目标替换或不明副作用不能自动扩大授权。

**最小任务 Interface。** 先恢复 `observe`／附近发现、容器读取／取放、`give-item` 等旧工具的任务语义，再为本次“取物交还”提供一个受约束的组合入口；沿用操作查询、聊天与独立停止。底层原子工具保留给 Adapter、调试及有支持的特殊操作，不能与正在执行的任务形成两条并发写入路径。首版不增加任意自然语言执行器、通用 DAG 或每一步都需模型批准的编排器。正常明确场景的目标是一次目标观察、一次任务提交，由程序完成中间步骤；异步终态一次返回，歧义才额外交流。数量是设计目标，需真实复测，不是现有速度结论。

“交还”结果必须区分已取出、当前持有、已丢出、目标玩家已拾取。只有可归因于指定玩家和指定物品数量的权威拾取证据，才说玩家已收到；掉落实体消失不够。部分完成或未确认要如实报告，不重复丢一份。自动走近先支持有界的安全平地绕障和满足触及距离／视线的站位；不挖路、搭桥或传送。特殊菜单与复杂地形仍需要明确 Adapter 或能力声明。

**调度和反馈。** 移除明确空闲请求无差别等待 1.5 秒的策略；同一玩家的连续补充按有上限的合并策略处理，缺少意图的半句话不能先执行。稳定公开常用任务工具，核验不同 Agent 的工具发现机制，避免每次普通操作都重新搜索低阶工具。按任务状态变化发必要进度，不机械刷屏，不编造百分比。主动查询已向模型交付的终态不再唤醒一轮；尚未交付的异步完成、失败或需要澄清仍必须通知一次。简化日志给模型的投影，原始权威结果保留用于排查。

叫停冷启动优化排在正确性之后：当前可靠的撤销／终止兜底保留；只有对应 Agent Adapter 能证明旧回合结束、旧工具连接不可继续发指令且新控制安全建立，才复用进程或会话。不能靠放宽旧租约／代次来获得速度。此前 `server-body-control.mjs` 在 `onNewTask` 接受前推进游标的缺陷已可控复现并修复：watch拒收保留、取消收尾时队列接收、旧Agent退出后投递一次；Claude／Codex模拟进程均已回归。当前仍保留叫停后开新会话。

### 三类玩法与分批交付（2026-10-03 用户确认）

旧路径已有陪挖 `escort.ts`、`bot-scripts/` 有限采集／矿道脚本，以及蓝图、材料准备和批量建筑能力。这些是迁移参考；旧陪挖未完成真人验收，旧建筑部分已有试玩，均不能直接视作新 ServerBody 已支持。新身体已完成持续跟随／等待、共同状态／停止机制及有限采集／拾取。下表是三类完整目标；持续陪挖、矿道与建筑仍待交付。

| 类别 | 用户表达示例 | 执行与结束方式 |
| --- | --- | --- |
| 持续模式 | “跟着我”“陪我挖矿”“只捡东西，别自己挖” | 保存当前陪伴意图，由程序在能力范围内持续执行；聊天不默认取消。玩家离线、危险或路径受阻时进入明确的等待／受阻状态，不无休止重试；叫停立即结束控制 |
| 有限任务 | “采些原木”“拿一组圆石”“挖十格矿道” | Agent 决定目标、范围和数量，再提交明确、有上限的任务；程序完成重复步骤，到量结束，受阻或叫停时报告已完成部分 |
| 建筑预设 | “在这里搭一个小棚子” | 选模板、位置、朝向，给材料清单和可理解的预览；场地明确后按顺序施工，遇缺料／冲突暂停，报告已放置与剩余项 |

三类共用任务状态、互斥、进度与停止机制；建筑预设内部也运行有限步骤，不再另起一套身体控制。Agent 负责意图、目标、数量选择、必要澄清及交流；Agent 主机上的共享任务层负责重复执行，Body／Adapter 提供真实状态与原生动作。普通聊天仍可响应，不让每挖一格、放一格都等待模型。这里只调整玩法职责，自动思考档位仍是另一项未实现的设计。

**数量规则：**

- 用户给出数量时优先遵从，区分“新采集 32 个”“背包补足到 32 个”和“交给玩家 32 个”；不要把挖了多少方块当作获得了多少物品。无法完整完成时如实报告部分结果。
- 用户没给数量，由 Agent 根据用途、现有材料、背包空间、工具与附近资源自主选择合理的有限目标，并在开工回应中说明，例如“我先采 24 个原木”。不为了缺一个数量反复询问，也不由程序一律补成 64／1 组；执行层仍必须收到明确目标和边界，不能无限采集或悄悄滚动追加。
- **1 组＝选定实际物品栈当前有效的最大堆叠数量**，由游戏端权威提供，考虑 Mod、服务器规则及组件影响：可能是 64、16、1 或其他上限。不是当前不足额栈的剩余数量，也不是某个特殊机器槽的容量。多组按该上限换算，执行时重新核验；上限改变不能悄悄改变已承诺的目标。
- 同 ID 的不同组件物品继续分别处理，不能为凑数合并不兼容变体；上限未知时先获取实际信息，不从 ID 或静态表猜 64。尚无实际物品、无法核验上限时说明未确定，不能声称已解析“1 组”。
- 任务总目标与单次动作的安全执行上限分开。大于一栈的目标由有限批次完成，保留每步物品／菜单核验、取消和 unknown 不盲重试；不能通过静默截断数量来满足当前接口限制。

**当前数量能力与边界：** 游戏端实际`ItemStack.getMaxStackSize()`已投影到背包、菜单和地面物品，保留完整组件核验。有限任务接收`count|stacks`之一，解析后目标最多256个，步骤／时间另有预算；程序不默认补64。原生拾取收据单独统计本次新获得量，不用旧库存或挖块数冒充。容器仍要求单个足量源栈与空快捷栏；99上限单栈取物／交物已实测，底层丢物保留每次最多64，由任务分批执行。跨源栈转移、背包补足目标尚未提供专用语义，不能冒称已交付。16／64／组件修改99已实际验证；99不是额外内容Mod已兼容的证明。

这两项是对已修缺陷的回归，不再扩大 V0 功能。此前用户确认的“不退服”来自模型处理停止的路径，不能替代最新宿主直接控制路径的实测；草方块已交还，但修复后首次交还仍需确认。一般聊天延迟不设未经测量的通过门槛，不将端到端耗时当作 TPS。

协议抽取后已新增 Codex 有状态连接适配，包含线程／回合、MCP 配置和取消。它仍不称为最终完整 AgentAdapter：Agent 与 MCP 进程仍耦合。已保留的 ClientBody 实验把真实客户端置于独立进程，通过租约接管，Agent 重启不关闭客户端；这项重启行为已做离线验证，游戏表现待验。ServerBody 已完成 A 的控制租约／宿主接线和 B 的交互／重生，真实模型仍由 C 单独验收，不能直接套用客户端结论。

## 试玩脚本

选安全区域，依次进行：打招呼 → 查询状态 → 跟随一小段 → 执行明确的小任务 → 用户叫停 → 说明完成及未完成部分。随后验证断线恢复与控制权互斥。原型测试用明确可改动的位置和独立资料目录，不借试玩改动已有建筑或人物记忆。

V1 再增加：内容 Mod 方块的碰撞和挖放、容器核验、退出重连、死亡重生及跨维度。每项分别记录“离线通过”“游戏通过”“未验证”，不能互相代替。

## 本轮不扩大的范围

- 不同时扩大 ServerBody 和 ClientBody 的完整功能；当前仅实施 ServerBody 有限验证组件，不全面迁移。
- 不要求首版恢复所有复杂建造、机器玩法、多 Bot 和跨平台桌面功能。
- 不做不可信插件市场、执行中切换身体或任意 Mod 自动理解。
- 不为了发布先重排整个仓库；必要的接口抽取由具体流程推动。
- 自动思考路由、全面视觉、语音和一般响应速度优化不抢在新身体可玩闭环前面；阻断可玩的明确缺陷才优先修复。

## 推进方式

Codex 负责拆任务、实现、回归、风险定位和维护本清单；用户参与目标变化、凭据配置及关键试玩体验反馈。普通实现选择继续自主推进。

修改实际客户端实例、服务器配置／模组或存档前，遵守 `AGENT.md` 的环境变更规则，先把可审阅的构建、影响和操作步骤准备好；本清单不代表已经安装或获得游戏内实测结论。用户密钥不写入仓库、日志或交接包。

每个里程碑完成后记录实际产物和遗留问题；性能、SDK 和框架优化由测量及试玩反馈决定。已有少量单轮耗时样本，尚无可对比性能基线，不承诺未经验证的人日、日期或 TPS。
