# MCBOT 通用适配方向与实施计划

2026-10-02。状态：V1 最小 ClientBody／客户端控制 Mod 正在实现，游戏兼容验收与适配 SDK 尚未交付。

**当前约束与复评优先：Agent 默认本机、可选另一台机器；本机低负载；用户已接受服主安装组件。[架构可行性复评](../architecture_reassessment.md)覆盖下文的旧选型：本地双客户端撤出默认主线，ServerBody 已获准有限验证，实验已有部分实测，尚非正式交付，见 [验证记录](server_body_validation.md)。下文保留此前客户端方案依据，不能继续当作开工指令；当前排期见 [交付清单](../delivery_plan.md)。**

用户进一步明确服务端正常运行开销是合理成本，不纳入本轮方案取舍；下文旧客户端资源预算不再作为 ServerBody 的验收前提。

本文件是当前兼容架构的主计划，取代 `neoforge_compat_plan.md` 中以自有 NeoForge 服务器为前提的主线选型与阶段安排。旧文档保留为协议限制、服务器假玩家及迁移风险的历史调研。

## 1. 产品目标与选型依据

### 用户明确的目标

从一开始就面向多数 Mod／服务器的适配，服务于其他玩家和不同服务器，不以玩家自己的服务器或服主权限为默认前提。提供开放接口和容易使用的适配方式，并考虑多个 Minecraft 版本。

同时支持不同 Agent 与原生 API Key 接入：首批目标包括 DeepSeek 官方 Harness、Codex、Antigravity；另提供不依赖外部 Harness 的内置 Agent 循环。详细设计见 [多 Agent 与原生 API 接入计划](../agent_integration_plan.md)。

### 根据目标确定的工程方向

- **真实 Minecraft Java 客户端 + 客户端控制 Mod 为主线。** Bot 使用目标服务器要求的兼容客户端环境，通过正常玩家交互执行动作；MCBOT 的基础陪玩不要求远端服务器安装 MCBOT 组件，也不要求 OP、RCON 或服务器文件访问。
- TS 侧保留并逐步解耦陪玩决策、记忆、事件、任务调度和保护规则，通过稳定的 `Body` 契约连接身体。
- Mineflayer 保留为原版及经过验证的兼容环境的轻量后端。它不是通用内容 Mod 的默认实现，也不是任何世界均能使用的回退后端。
- 服务端组件是可选增强：需要服主配合时提供额外信息或专用能力。完整服务器假玩家后端是后续可选路线，不作为通用适配交付的前置工作。
- 先使用正常渲染环境验证客户端控制；低画质、限帧和资源管理属于主线工程，无头化另行验证，不以无头运行成功作为基础兼容的前提。

真实客户端主线是针对上述目标的工程选型，不表示已经证明能兼容多数 Mod。若原型失败，应说明原因、修订方案；不能悄悄退回“只支持自有服务器”的产品范围。

## 2. “多数”怎样成为可验证的目标

长期目标是扩大通用覆盖面；每次发布只声明实际测过的组合和功能。当前没有足够样本，不能给出兼容百分比。

| 适配对象 | 应提供的路径 | 必须分开验证的事项 |
| --- | --- | --- |
| 原版与原版协议兼容服务器 | 客户端通用能力；可选 Mineflayer | 登录、聊天、移动、容器、挖放及服务器行为差异 |
| 服务端插件服 | 普通玩家客户端 + 服务器配置／功能适配包 | 菜单、命令、资源包、领地规则和服务器自定义玩法 |
| 内容 Mod 服／整合包 | 兼容的真实客户端实例 + 对应版本／加载器的控制 Mod | 实例能运行、能进服、基础操作正常、特定玩法可操作 |
| 需要自定义界面／按键的 Mod | 客户端功能适配器 | 界面状态、操作流程、客户端事件、结果确认 |
| 愿意安装增强组件的服务器 | 上述基础能力 + 可选服务端增强 | 新增能力与权限明确；移除增强组件后基础路径仍可工作 |

“多数”不等于所有任意组合、自动理解全部机器或绕过服务器准入条件。服务器仍可限制客户端 Mod、自动化、账号及交互；客户端技术兼容不能消除这些条件。当前范围是 Minecraft Java，基岩版另行立项。

采用代表性样本清单跟踪覆盖：服务器类型、目标整合包、MC／加载器／Mod 版本、已验收功能、失败原因、维护者。样本先覆盖不同交互类型，再逐步扩大；不能只在自己的 NeoForge 服上验收后宣称通用。

## 3. 架构边界

```text
外部 Agent 适配器 / 内置 API Agent Runtime
        │
MCP 工具、记忆、行为规划、任务与权限策略
        │
能力目录、结构化结果、Body 契约
        ├─ ClientBody ── 本机控制通道 ── 真实客户端 + 控制 Mod（主线）
        │                                      │
        │                         MC 版本绑定 / 加载器绑定
        │                                      │
        │                         Mod 与服务器功能适配器
        └─ MineflayerBody（兼容环境的轻量后端）

可选：经授权的服务端增强，为 ClientBody 提供额外能力。
后续：确有需求时实现 ServerBody，不要求与客户端主线同时完成。
```

- Body 契约不向上返回 Mineflayer Bot、Java 对象或具体寻路 Goal；统一坐标、单位、命名空间 ID 和数据来源。
- **核心不绑定 MineflayerBody。** 它是可选后端；ClientBody 基础运行不得要求安装、加载或启动 Mineflayer。当前实现仍有直接依赖，需迁移后才能满足此验收标准。
- Agent runtime、模型供应商、Body、人设和游戏环境分别配置。更换 Agent 不要求更换身体；所有 Agent 和 API 通道共用工具、任务保护与记忆边界。
- MC 版本绑定处理游戏 API、组件和交互变化；加载器绑定处理事件、注册与平台接口。包含 MC 类的 Java common 代码仍可能受版本限制。
- Mod 适配处理特定玩法；服务器适配处理插件菜单、命令约定和规则。相同 Mod 在不同服务器配置下也可能有不同操作条件。
- 客户端只承诺可观察到的信息。客户端预测、已同步状态和服务端增强返回的信息应区分；不假定可以读取未同步的机器内部状态或配方。
- 核心不依赖某一个模型供应商、固定 Bot 名、本机服务器路径或特定模组。现有启动器和驱动器先保持可用，通过边界逐步迁移。

## 4. 三种扩展方式

| 方式 | 能做什么 | 不能替代什么 |
| --- | --- | --- |
| 配置适配包 | ID／标签分类、保护策略、已有菜单模板映射、命令格式、已有交互模板参数 | 不会凭配置创造不存在的客户端能力或理解任意机器 |
| 行为脚本 | 组合查询、移动、交互、等待、核验和中断 | 不直接操作原始连接、任意 Java 对象或本机账号文件 |
| 客户端原生适配器 | 调用目标 Mod 的客户端交互流程、界面和专有 API | 不代表所有版本均兼容；按 MC／加载器／Mod 组合编译与测试 |

适配包以静态清单声明名称、版本范围、能力、参数／结果、依赖及权限；浏览清单不执行脚本。第一版面向用户明确安装的可信适配器，不包含不可信插件市场。

优先组合通用能力：移动、转向、挖放、使用、标准容器、菜单观察和点击、聊天及按键。对通用模板无法覆盖的功能开放原生扩展点。GUI 不是一律依赖截图坐标；先利用可用的结构化界面信息，特殊界面由适配器处理，必要时再使用视觉辅助。

提供适配检查器：显示目标 ID、可观察状态、已匹配模板、可用／缺失能力和原因，并能生成配置骨架。能力目录应区分“环境具备能力”和“当前目标满足执行条件”。

验证扩展机制的标准：新增代表性适配包时，上层核心不需要加入该 Mod／服务器的专用分支；确实发现通用能力缺口时，补充通用接口并更新契约测试。

## 5. 跨环境必须提前处理的契约

- **观察**：批量局部快照；区分未加载、未知、不存在和空气。实体、物品、菜单句柄绑定当前世界／会话，不在重连后盲用。
- **执行**：结构化输入、结果与可读摘要；操作 ID、结果查询、参数一致性检查。区分接受、执行、成功、失败、取消、部分完成和结果未知。
- **取消**：失去控制权、退出世界或连接断开时停止持续输入；超时不等于无副作用，重连后不能盲目重发投料、丢物品、放置等动作。
- **仲裁**：第一版单个独占身体动作通道，聊天与允许的查询可并行；用户停止／接管、避险、任务、跟随和空闲的优先级明确。一个玩家只有一个动作执行者。
- **保护**：核心预检查，客户端执行前再核验可观察的目标、距离、当前物品、任务范围和权限。客户端检查不能代替远端服务器的裁决；等待同步结果后确认成败，不把客户端预测当作服务器成功。
- **服务端增强**：仅声明新增能力，不能成为基本动作的隐性依赖。不得因能力不足自动改用 OP 命令、RCON 或直接改世界。
- **身份与账号**：Bot 作为独立玩家时，需要与主人可同时在线的身份，并满足目标服务器认证／白名单要求。不能默认继承当前离线模式的 Claude UUID、库存和身份；也不能默认接管用户正在玩的客户端。
- **环境资料**：按用户选择的服务器／世界配置隔离地点、建筑、库存知识和世界记忆，显式关联稳定 worldId。不要只用服务器地址判断世界身份。
- **本机控制**：控制通道与远端游戏连接分离，默认只监听本机并鉴权；控制 Mod 不给远端增加基础玩法必需的自定义频道。联网兼容须在未装 MCBOT 的服务器上验证。

## 6. 多版本与多加载器

从第一版就保留版本与加载器边界，按明确组合构建和发布。目标是大脑和适配语义可复用，不承诺一个 jar 覆盖所有版本。

- 当前 1.21.1 NeoForge 可用于第一个原型，原因是已有调试环境；它不是产品支持范围的上限。
- 在核心接口尚可调整时，引入第二个 MC 版本和第二种加载器的小规模契约验证，分别改变一个维度，避免全量迁移后才发现抽象错误。
- 具体第二版本与加载器按代表性目标整合包、用户需求及可维护性选择；尚未决定采用 1.21.4。1.20.1 Forge、Fabric 等也不作未经验证的支持承诺。
- 各构建跑同一套基础契约场景；Mod／服务器专属测试由适配包补充。版本支持按连接、观察、基础动作、陪玩流程、专用功能和视觉分别记录。
- 原型允许只验收少数功能；对外发布必须列明未实现部分。语音、附魔和桌面截图分别有自己的兼容范围，不能由 Body 的版本支持自动推导。

## 7. 分阶段实施与验收

### P0：客户端主线可行性与接入边界

先做最小客户端控制原型，不同时建设两个完整新后端。验证独立玩家身份、连接、状态、聊天、移动／停止、单次挖放、容器与取消，保持正常渲染环境。测资源占用和主人客户端帧时间；记录基线后再定性能预算。

至少覆盖：未安装 MCBOT 服务端组件的原版兼容服务器，以及兼容客户端环境中的内容 Mod 服务器。增加一种有区分度的特殊交互。另验退出重连、死亡重生、跨维度、失去控制端和服务器拒绝操作。

通过标准：基础闭环不需要服主安装组件；结果来自正常游戏同步；退出／断连后旧动作不再继续；目标客户端环境能加载控制 Mod。若失败，记录是实例、认证、协议、动作还是 Mod 语义问题，分别处理。

### P1：最小 Body 契约与旧功能保留

先贯通状态／聊天、取消、移动和单次交互；Mineflayer 与 ClientBody 使用同一上层流程。行为测试使用假 Body，后端保留专属测试。用一条完整流程推动接口设计，不先抽象所有工具。

同步提取 AgentAdapter 和 ProviderAdapter，按 `agent_integration_plan.md` 用假 Body／现有身体先验证外部 Harness 与原生 API 两条路径。它们不必等待完整 ClientBody；新身体也不绑定某个 Agent。随后验收 DeepSeek Harness、Codex、Antigravity 的工具接入及托管接入。

建立当前能力清单，迁移时逐项标记保留、完成或暂缓。随后恢复建造、战斗、本能、跟随、记忆和事件，验证中断后重查状态再继续的陪玩闭环。

### P2：扩展机制与跨环境验证

制作一个通用内容配置包、一个特殊 Mod 功能适配器和一个服务器插件玩法适配包；目标实例与功能清单在测试前明确。

同期做第二 MC 版本和第二加载器的有限验证，确认主要差异留在绑定层，核心任务和行为脚本不必按环境重写。各环境不要求一次恢复全部功能。

### P3：开发者预览与扩大覆盖

发布稳定程度明确的接口文档、清单格式、类型化脚本 SDK、示例适配器、检查器及契约测试。安装诊断应说明缺少的是游戏版本、加载器、Mod、适配器还是服务器权限。

建立官方验收、社区维护、实验性三类兼容记录；按代表性样本扩大覆盖，记录完整版本组合和功能结果。后续再评估服务端增强、完整 ServerBody、无头化、多 Bot 与其他操作系统。

## 8. 当前实施前仍需确定的参数

这些问题用于排实施顺序，不再重新讨论“是否只服务自己的服务器”：

- 第一批具有代表性的 Mod 功能、整合包和服务器插件玩法。
- 第二 MC 版本、第二加载器以及正式维护组合数量。
- 独立 Bot 账号／客户端实例的接入方式和资源预算。
- 第一轮必需的陪玩与视觉能力。

本计划不沿用旧方案的“12～18 个会话”估算，也不把外部评审的人日／性能建议视为承诺。原型完成后按实测工作项重估。
